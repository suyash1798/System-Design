# Payment System – System Design

## Problem definition
Design a Stripe/Razorpay/UPI-like payment system where:
- A user pays a merchant
- Money moves exactly once
- The system survives retries, crashes, and network failures

Golden rule: money must move exactly once, or not at all.

## Scope (lock this early)
### In scope
- Payment initiation
- Authorization
- Capture (money movement)
- Payment status (INITIATED / AUTHORIZED / SUCCESS / FAILED)
- Idempotent retries
- Failure recovery

### Out of scope
- Refunds
- Chargebacks
- Disputes
- Subscriptions
- KYC/compliance
- Multi-currency

## Core guarantees
- Exactly-once money movement
- Idempotent execution
- Durable transaction records
- Consistent final state
- Secure handling of payment data

If any of these break, the system is invalid.

## Key components
- Payment API – entry point for merchants
- Payment Service – owns the state machine
- PSP/Bank Gateway – external money mover
- Ledger/DB – durable state
- Reconciliation Worker – failure recovery

Note:
- Client never moves money
- Client never talks to PSP directly

## Payment state machine
```
INITIATED
   ↓
AUTHORIZED
   ↓
CAPTURE_IN_PROGRESS
   ↓
SUCCESS / FAILED
```

Rules:
- State only moves forward
- Every transition is persisted
- No external call without a stored state

## Successful payment flow (step-by-step)
1) Merchant → Payment API
   - Create payment_intent
   - Include idempotency_key
   - Persist state = INITIATED
2) Client → PSP (tokenized card)
   - Server never sees raw card data
3) Payment Service → PSP
   - Authorize payment
   - Persist state = AUTHORIZED
4) Before capture
   - Persist state = CAPTURE_IN_PROGRESS
   - Store provider_txn_id
5) Payment Service → PSP
   - Capture payment
6) On success
   - Persist state = SUCCESS
   - Notify merchant

## Idempotency
### Idempotency key
- Generated by merchant; unique per logical payment

### Where enforced
- Payment Service (before any PSP call)

### Retry behavior
- Same key → return stored result
- Never re-execute authorization or capture
- Retries return state; they must not re-charge money

## Exactly-once semantics
- System uses at-least-once execution
- Combined with idempotency → effectively-once money movement
- Exactly-once ≠ no retries
- Exactly-once = retries without side effects

## Failure handling
1) Merchant retries payment request
   - Same idempotency_key → return existing payment state
   - No duplicate charge
2) Authorization succeeds; service crashes before capture response
   - State already = CAPTURE_IN_PROGRESS
   - Recovery job queries PSP using provider_txn_id
   - Transition to SUCCESS or retry safely
3) Capture succeeds but ACK lost
   - PSP captured money
   - Retry returns SUCCESS; never call capture again
4) Network timeout during capture
   - Do NOT retry blindly
   - First reconcile with PSP
   - Retry only if PSP confirms not captured

## Recovery & reconciliation
### Why needed
- External systems are unreliable; ACKs can be lost; crashes happen mid-flight

### How it works
- Periodic job scans AUTHORIZED and CAPTURE_IN_PROGRESS
- Queries PSP and moves state forward safely
- External calls are reconciled, never replayed blindly

## Data model (simplified)
### PaymentIntent
```
payment_id
idempotency_key
amount
state
provider_txn_id
timestamps
```

Indexes:
- idempotency_key (unique)
- provider_txn_id

## Security
- Card data tokenized via PSP; server never stores raw card info
- TLS everywhere
- Limited access to payment APIs

## Key principles
- “Money must move exactly once or not at all.”
- “Retries return state, not re-execute money movement.”
- “Every external call is preceded by a durable state transition.”
- “Idempotency keys convert at-least-once execution into exactly-once behavior.”
- “Reconciliation makes the PSP the source of truth after failures.”
